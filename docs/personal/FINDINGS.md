# Taala2/bcd-personal: выводы, проверенные гипотезы и порядок проверки

Документ ведётся по правилам «BCD Personal — Engineering Workflow». Факты, гипотезы и непроверенное разделены. «Проверено» означает одно из трёх, и каждый раз указано, что именно:
- **CI** — CI зелёный;
- **host** — проверка на хосте (Windows, без компилятора C и Swift: только Python-части);
- **устройство** — проверено на телефоне.

Устройство: iPhone16,1 (8 ГБ, лимит iOS 6143 МБ), iOS 27.0.1, приложение «BCD 2» (Madeira2 IPA), сборка 627.

## 1. Порядок проверки на устройстве

1. Сборка: `gh workflow run build-ipa.yml --repo Taala2/bcd-personal --ref sync/0.1.626`. Сборка занимает около 55 минут.
2. Репозиторий публичный, поэтому артефакт `madeira-unsigned-ipas-0.1.<N>-encrypted` содержит только `.ipa.enc` и хранится 3 дня. Расшифровка:
   `openssl enc -d -aes-256-cbc -pbkdf2 -iter 200000 -md sha256 -in Madeira2-0.1.<N>-unsigned.ipa.enc -out Madeira2-0.1.<N>-unsigned.ipa`
3. Подписать и установить поверх «BCD 2».
4. Правило из списка рекомендаций попадает в игру при первом появлении игры или если её конфиг не меняли. Если конфиг менялся, нужно нажать «Reset to Recommended».
5. Присылать нужно обычный `bcd-log*.txt`. Файл `.prev` нужен только тогда, когда приложение закрылось и обычный лог той игры не сохранился.
6. Какие строки в логе подтверждают, что сработало нужное:
   - `[recs] personal list v<N> ...` — загружен личный список правил;
   - `[game-cfg] ...` — с каким конфигом шла игра;
   - `[personal-default] NAME=1` — включён общий ключ;
   - `[wasm-guard-trim]`, `[anon-ldadd] personal ... width=8`, `[tls-cross-clear] ... SPARED` — сработал ключ;
   - `[reloc-bounds]` — сработала проверка границ таблицы релокаций;
   - `[bcd] library launch <exe>` — какой exe запущен.

## 2. Подтверждено на устройстве

### Internship [demo] (NW.js 0.48, RPG Maker MZ, x64)

Игра работает около 6 минут на 57–60 fps (2026-11-02). Каждая причина ниже подтверждена своим запуском, а каждый ключ проверялся отдельно.

| Симптом в логе | Причина | Ключ |
|---|---|---|
| Chromium `Check failed: current` (sequenced_task_runner_handle, thread_task_runner_handle) | `TlsFree` в одном псевдопроцессе обнуляет TLS-слоты 4 и 5 во всех потоках всех процессов | `env.MADEIRA_TLS_CLEAR_OWN_PROCESS = 1` (запуск 7: 170 `SPARED`, 0 FATAL) |
| `[jit-pool] EXHAUSTED ... nw.dll`, `Failed to load NW DLL` | Каждому дочернему процессу Chromium нужна своя копия nw.dll (138 МБ) в JIT-пуле | `env.MADEIRA_X64_IMAGE_NOCOPY = 1` (запуск 4) |
| `[store-undecoded] insn=0xf8e800c6 ... alias OK`, `[mach_exc] UNHANDLED` | 64-битный LDADDAL на анонимном RX-алиасе кучи V8 | `env.MADEIRA_ANON_LDADDAL64 = 1` (запуск 12: 16 строк `width=8`, 0 UNHANDLED) |
| 64 отказа на резервирование `size=0x280000000` | V8 8.5 резервирует 10 ГБ под каждый `WebAssembly.Memory` (`kFullGuardSize = 10 GiB`), и флагом это не отключить | `env.MADEIRA_WASM_GUARD_TRIM = 1` (запуск 15: 6 ГБ выдано, 0 отказов) |
| `[jit-pool] EXHAUSTED (anon RWX)`, `Fatal process out of memory: wasm code commit` | Пул в 624 МБ мал для wasm-кода V8 | `pool-split = 1`, `pool-low = 1` (запуск 16: нет EXHAUSTED и Fatal) |
| Тёмный экран, AudioService не может загрузить nw.dll | Урезанные 4 ГБ попали внутрь окна образов | Исправлено размещением только выше `0x73ffff0000` (e3b26c7) |

Не доказано, что нужны `MADEIRA_X64_NOCOPY_DATAIMP` и `MADEIRA_THREAD_STACK_SPILL`: оба были в рабочем конфиге, но отдельной проверки не было.

### Прочее на устройстве

- Правило upstream `nwjs-game-exe` (`MADEIRA_CHILD_ARGS`) передаёт аргументы и в `--type=crashpad-handler`. Тот завершается с ошибкой `invalid option -- 'd'`, и игра не стартует (запуски 1–2).
- Закономерности первой серии из 14 игр (2026-11-02/03, сборка b3b1643) описаны в разделе 4.

## 3. Опровергнутые гипотезы

- **Флаги отключения trap-handler для wasm** (`--disable-features=WebAssemblyTrapHandler --js-flags=--no-wasm-trap-handler`) убирают 10-гигабайтные резервирования. Опровергнуто запуском 13: флаги дошли до рендерера, а 65 запросов `0x280000000` остались.
- **`MADEIRA_CAGE_RELEASE = 1`** помогает Internship. Опровергнуто запуском 10: стало хуже, рендерер умер.
- **Видеофлаги в конфиге одной строкой** доходят до Chromium. Опровергнуто запуском 6: в `argv` их нет. Аргументы задаются только полем «Launch arguments».
- **the-quiet-song-of-plants падает из-за отсутствия AVX.** Опровергнуто 2026-11-03 (сборка e66e3f5). С `avx=1` (`[fex-avx] ... AVX and AVX2 reported and emulated`) падение то же, что с `avx=0`: INT3 в `The Quiet Song of Plants.exe+0xcd2700` при тех же значениях RAX/RBX/RCX/RDX.

Подтверждено исходниками или кодом, но не на устройстве:
- `opengl32.dll` в BCD — заглушка (`[unixlib] opengl32 (GL-absent stub table)`). Upstream-правило `opengl-only-no-context` помечено как неисправимое (noFix).
- Ren'Py (`renpy/display/presplash.py`, `core.py`):
  - если задан `RENPY_LESS_UPDATES`, заставка не показывается, а переходы между сценами отключаются;
  - `RENPY_RENDERER` выбирает отрисовщик; на Windows порядок такой: `gl2 → angle2 → gles2 → sw`.
- Внешние переменные окружения передаются Windows-программе без фильтра (`build/ntdll-unix/env_ios.c`, `get_initial_environment`).
- Нехватку памяти обрабатывает upstream auto-tune (`swap-8gb-memory-kill*`). Подкачка включается только после вердикта «killed», то есть со второго запуска.
- Python в Ren'Py выполняет `cmd /c ver`. ARM64-процесс `cmd.exe` падает в хуке FEX (`libarm64ecfex.dll+0x1130dc`, адрес 0x38, cpuarea=0). Игре это не мешает: процесс убирается.

Изменения после этой серии (10db375, CI 41500754292 зелёный). Что показала вторая серия, описано в разделе 7.
- `virtual_ios.c` `[reloc-bounds]`: таблица релокаций и записи за пределами образа больше не применяются. Это проверяет гипотезу для lucieneslife.
- `GameLibrary.swift`: `python.exe` и `pythonw.exe` больше не выбираются как программа игры.
- `personal-renpy`: `RENPY_LESS_UPDATES = 1` и `RENPY_RENDERER = angle2`. **Здесь две переменные в одной итерации.** Их можно различить по логу (`[guest-log]` дублирует `log.txt` Ren'Py, где виден выбранный отрисовщик), но если ANGLE не заработает, следующая итерация — оставить только `RENPY_LESS_UPDATES`.

Открытые гипотезы, ещё не проверявшиеся:
- Way of Corruption: деоптимизатор V8 32-бит под FEX. Эксперимент: «Launch arguments» `--js-flags=--no-opt`.
- the-quiet-song-of-plants: AVX проверен и не помог (раздел 3). Следующий шаг описан в разделе 7.
- Minami: данных нет. Нужен лог с `env.MADEIRA_GUEST_LOG = all`, он уже включён правилом.

## 5. Общие ключи для всех игр (b3b1643)

`WineProcessBridge.m` выставляет `MADEIRA_TLS_CLEAR_OWN_PROCESS`, `MADEIRA_ANON_LDADDAL64` и `MADEIRA_WASM_GUARD_TRIM` в 1, если ни `bcd.cfg`, ни конфиг игры их не задают. Каждый ключ срабатывает только там, где без него ошибка. Риск регрессий у игр, которые уже работали, на устройстве не измерялся. Если такая игра сломается, ключи проверяются по одному через `env.NAME = 0`.

Каталог настроек для этих ключей по-прежнему показывает «Default off». Это известное расхождение.

## 5b. Память: куда уходит (разбор логов 2026-11-04, без кода)

Полосы из `[phys-map] bands` (грязные/резидентные МБ) и footprint по играм:

| Игра | Footprint | Пул RX (весь пул, грязный) | Занято в голове пула | FEX | Гость | Не в полосах |
|---|---|---|---|---|---|---|
| lucieneslife (крошечная) | 1222 | 576 (весь, 0x24000000) | 11 МБ | 7 | 4 | ~0,6 ГБ (приложение) |
| CelSector (Unity) | 4904 | 608 | 102 МБ | 360 | 97 | ~2,2 ГБ (internal 1761 + compressed 939; остальное, видимо, IOKit/Metal) |
| V.0.7 (NW.js 64) | 5440–5908 | 880 + регион C 240 | ~362–434 МБ + хвост ~400 МБ | 925 | 2302 | ~0,5 ГБ |
| Succum (NW.js 64) | 5648–5763 | 880 | ~420 МБ | 778 | 2401 | — |

Факты:
- Пул «грязный с рождения»: его создаёт StikDebug. Исключить его из учёта jetsam upstream не смог (ml458, комментарий в `ContentView.swift`), поэтому платим за весь размер пула, а не за занятую часть.
- Размер пула можно задать для одной игры: строки `pool-above-window = 1` и `pool = N` (256–1152) в файле игры. Upstream пробовал 384 для игр без Steam/CEF (ml668).
- У NW.js-игр пул занят по-настоящему (голова, хвост, регион C), так что уменьшать почти нечего. У маленьких и Unity-игр 300–500 МБ пула пустуют.
- У Unity (CelSector) около 2,2 ГБ footprint не видно ни в одной полосе. **Поправка:** у CelSector обход полос выполнился только на `cycle=2`, то есть рано: обход идёт на cycle 2, затем раз в 30 циклов (`MADEIRA_WARMER_SWEEP_CYCLES`) и один раз при 90% лимита. А footprint вырос позже. Значит, «невидимые 2,2 ГБ» — несравнимые замеры, а не доказанная видеопамять. Гипотеза про ресурсы Metal остаётся непроверенной.
- Сборка-замер (2026-11-04, `virtual_ios.c`, только логирование):
  - `[footprint-ledger] madeira-bcd graphics=… media=… neural=… purgeable-nonvolatile=… network=…` из `TASK_VM_INFO` rev3: каждые 5 циклов и при изменении графики на 64 МБ и больше;
  - строки `ml1074 … dirtiest` теперь печатаются и для полос `guest` и `fex`.
  - Для замера в конфиге игры: `env.MADEIRA_WARMER_SWEEP_CYCLES = 5`, чтобы обход шёл примерно каждые 10 с.
- Полоса FEX — 0,36–0,93 ГБ, из чего она состоит, лог не показывает.

Глобального рычага на 1–2 ГБ разбор не выявил. Возможные рычаги: размер пула по движку (выгодно не-NW.js играм), FEX (неизвестный состав), ресурсы Metal у Unity (неизвестный состав).

### Результаты сборки-замера (17df614, 2026-11-04)

- `[footprint-ledger] graphics` (видеопамять по учёту ядра):
  - lucieneslife (Ren'Py, 2D) — 526 МБ;
  - CelSector (Unity) — 1154 МБ (+225 сжатых);
  - V.0.7 — 469–1146 МБ (+ до 1290 сжатых);
  - Succum — 0 (лог до старта рендерера).

  Видеопамять — заметная статья. Один из рычагов — upstream-ключ `env.DXMT_SMALL_RINGS = 1` (кольца по 4 МБ вместо 32 МБ), не проверен.
- **Полоса FEX**: самые «грязные» её области — стеки call-ret по 8 МБ (`0x804000`, [vname] `FEXMem_CallRetStacks`), по 7–8 МБ грязных каждый. При этом:
  - `[callret] zero-scrub rev=ml362 stale=0x0` во всех потоках (398 у V.0.7, 77 у Succum);
  - JIT стек не использует (`callret-elide-v1` по умолчанию).

  Значит, страницы приносит само чтение в `ZeroScrub` (FEX `AllocatorHooks.h`). Его комментарий исходит из поведения Linux («reading an untouched anonymous page maps the shared zero page»).
- **Исправление** (локально, не проверено): `tools/patch-fex-ios-callret-noscrub.py`. Пока стек отключён, при старте потока он не читается; `MADEIRA_FEX_CALLRET_ELIDE=0` оставляет всё как было. Ожидание — до ~8 МБ на живой поток, у NW.js-игр сотни мегабайт. Признак в логе: `[callret] zero-scrub skipped: the stack is elided`.
- Не тронуто (своя гипотеза): обнуление кэша переходов L1/L2 (`[TI-IC] zero-scrub`) — там нулевое содержимое нужно для правильной работы.

### Проверка на устройстве (4eb682e, сборка 627, 2026-11-04)

Строка `[callret] zero-scrub skipped: the stack is elided` есть во всех 4 логах. Строки `zero-scrub rev=ml362` нет. Стеки `0x802000` пропали из «самых грязных» областей FEX.

| Игра | Полоса FEX (грязные МБ), до → после | Пик footprint, до → после | Сессия после |
|---|---|---|---|
| V.0.7 (memcpy=1) | 925 → 382–392 | 5440–5908 → 4096 / 3826 | 43 с и 39 с, avg 29,5 (cap 30) |
| Succum | 778 → 440–454 | 5763 (jetsam после ~50 с) → 5185 | 110 с, 84 с игры, avg 45,5, 1 стоп 20 с |
| CelSector | 360 → 114 (оба на cycle 2), позже 176 | 4904–6097 → 4598 | 45 с, avg 49 |
| Internship | — → 424–426 | — → 5205 | ~2,5 мин |

- Экономия FEX — 330–530 МБ у NW.js-игр и ~250 МБ на старте у CelSector. Это совпадает с ожиданием «до 8 МБ на поток» (177–204 потока).
- Пики сравнимы лишь отчасти: сессии короткие (40–110 с).
- Итог по словам пользователя: Internship работает; V.0.7 не запустился; Succum вылетел; CelSector вылетает по «Start game». Разбор:
  - **Succum.** На 86 с рендерер упал по нехватке памяти внутри V8: `code=e0000008` (OOM-исключение Chromium), «Last few GCs: Mark-sweep (reduce) 15.4 → 15.3 MB, last resort GC in old space requested». Куча JS всего 15 МБ, footprint 4985 из 6143 — это не jetsam. Физической памяти игре сообщено 6143 МБ (`ullTotalPhys`), флаги V8 — только `--expose-gc`. Какое выделение не прошло, лог не показывает: ни одного `[nt-fail]` с фиксацией в клетке V8 (0x7800000000) перед падением; есть лишь обычные отказы по подсказке адреса (c0000018) и одна неудача JIT-пула FEX на 128 МБ (c0000017, FEX сам уменьшил до 64 МБ). Рядом 195 раз `[alias-tomb] STALE alias decommit REFUSED` на страницах клетки (0x78000ff000, 0x780023f000): освобождение отклонено, страница не обнулена. Связь с падением не доказана.
  - **V.0.7.** Вернулся старый сбой: переход в код из `0xCC` (`[entry-fail] … guest bytes cc cc …`, `UNMAPPED AT ENTRY (wild pointer)`), хотя `memcpyset=true` (в логе `vector=false`). **Поправка пользователя (устройство):** игра заходит, только если включены оба ключа, `FEX_VECTORTSOENABLED = 1` и `FEX_MEMCPYSETTSOENABLED = 1`; без любого из них сбой. Прежний вывод «достаточно memcpy» (2 сессии) неверен. Оба ключа включает пресет Compatibility.
  - У V.0.7 и Internship один и тот же `nw.dll` (размер образа `0x89b7000`, NW.js 0.48), но Internship идёт на 57–60 fps без этих ключей. Значит, нужда в строгом порядке зависит от нагрузки игры, а не от версии NW.js. У Succum `nw.dll` другой (`0x90a4000`); падал он с `vector=false memcpyset=false`. Гипотеза (не проверена): его OOM в V8 — тот же класс ошибок порядка памяти.
  - **Compatibility на Succum и Internship** (2026-11-04, 14:00–14:04, `vector=true memcpyset=true`):
    - Internship: ~55 fps за 2 мин (кадры 64 → 6720 за 121,6 с); без ключей было 57–60. Цена около 5%.
    - Succum: 95 с, 0 кадров, рендерер так и не запустился (`--type=renderer` — 0 раз) — второе такое зависание (первое в серии 2). Процесс браузера: ~14 потоков горячие в коротких копирующих функциях `nw.dll`, ~4,4 ядра, IPC 0,37. Без ключей Succum грузится за ~17 с. Значит, строгий порядок делает работу процесса браузера при запуске крайне медленной.
    - Сбой V.0.7 происходит в `CrRendererMain` (поток 0100), то есть в рендерере.
    - FEX читает настройки отдельно в каждом процессе: 12 строк `TSO config` у Internship, `LoadConfig(ExecutableName, _environ, …)` в `Source/Windows/ARM64EC/Module.cpp` (пин 959ac06). `VectorTSOEnabled`/`MemcpySetTSOEnabled` читаются при `CreateNewContext`, после места, где `patch-fex-ios-launcher-smc.py` уже меняет `SMCCHECKS` для одного процесса.
    - **Сделано локально (не собрано, не проверено на устройстве):** `tools/patch-fex-ios-renderer-tso.py`. В процессе с `--type=renderer` в командной строке (из PEB) FEX включает `VectorTSOEnabled` и `MemcpySetTSOEnabled` сразу после `CONFIG_IS64BIT_MODE`, до `CreateNewContext`.
      - Явный `FEX_VECTORTSOENABLED`/`FEX_MEMCPYSETTSOENABLED` в конфиге игры главнее, поэтому пресеты работают как раньше.
      - `MADEIRA_RENDERER_STRICT_TSO=0` выключает правило.
      - Признак в логе каждого процесса: `FEX: renderer-tso-v1 madeira-bcd renderer=… enabled=… vector=… memcpyset=…`.
      - `build-xtajit64.sh` применяет его для любого пина. Проверка: `tests/host/check-fex-renderer-tso.py` (шаг CI). На реальном пинованном `Module.cpp` (959ac06) накладывается вместе с launcher-smc, повторный прогон ничего не меняет.
      - Steam не затронут: CEF у него идёт с `--single-process`, без отдельных рендереров.
  - **Кэш переходов FEX (L1), сделано локально (не закоммичено, не собрано в CI, не проверено на устройстве):** `tools/patch-fex-ios-l1-reclaim.py`.

    - Локально: патч накладывается на пин 959ac06, `xtajit64.dll` собирается (строки патча есть в DLL), `tests/host/check-fex-l1-reclaim.py` проходит на настоящем исходнике.
  - **Идея «загрузить заранее»** (проверено по логам):
    - пул JIT во всех 6 логах урезан (`no hole fits a 896MB pool — SHRINKING to 560–624MB`), но `jit-rollover=0`: сбросов кода и связанных с ними фризов нет. Исключено.
    - в FEX есть незаконченный кэш переведённого кода на диске (`EnableCodeCachingWIP`, `FEXCore/Source/Interface/Core/CodeCache.cpp`), но ARM64EC-модуль его не подключает (0 упоминаний в `Module.cpp`). CelSector переводит ~105 тыс. блоков. Большая работа.
